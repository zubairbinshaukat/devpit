# Docs site contract

Read this before adding pages. It is the agreement between the infrastructure
author, the content author (Troubleshooting pages, blog posts) and the
screenshot agent. Live at https://devpit.zubyr.dev/docs, built with Astro 7 and
Starlight 0.42, blog by starlight-blog 0.30.

## Run it

```sh
cd web/docs-site
npm ci                 # Node 22 (>= 22.12). Exact versions are pinned.
npm run dev            # http://localhost:4321/docs
npm run build          # writes web/docs-site/dist (base /docs)
npm run check          # after a build: meta, JSON-LD, assets, shots (and the site checks below)
```

`npm run check` needs a finished `npm run build` first. The whole site (landing
page plus docs) is assembled by `node web/scripts/build.mjs`, which is what
Vercel runs; with that done, `npm run check` also checks the merged sitemap,
robots.txt and llms.txt. `node web/scripts/serve.mjs` serves `web/dist` the way
Vercel does (clean URLs, compression) for a look in a browser. You do not need
any of this to write pages.

## Directory layout

```
web/docs-site/
  astro.config.mjs        Starlight, plugins, sidebar wiring
  site.config.mjs         SITE, BASE, sidebar (edit here to add a nav entry)
  shots.json              screenshot manifest for the docs pages (see "Images")
  shots.content.json      screenshot manifest for troubleshooting and blog (content author)
  src/content/docs/       ALL pages (.md or .mdx); path = URL under /docs
    index.mdx                       /docs
    getting-started.mdx             /docs/getting-started
    features/<slug>.mdx             /docs/features/<slug>
    troubleshooting.mdx             /docs/troubleshooting (hub, lists the folder automatically; do not edit)
    troubleshooting/<slug>.mdx      /docs/troubleshooting/<slug>      <- content author
    blog/<slug>.mdx                 /docs/blog/<slug>                 <- content author
    command-line.mdx                GENERATED by `task docs:cli`, never edit by hand
    whats-new.md                    GENERATED from the GitHub releases (`npm run whats-new`)
  src/assets/screens/     screenshots <name>.webp, rendered by `task docs:shots` (see "Images")
  src/assets/             other images used by pages (covers, diagrams)
  src/components/         Shot.astro, SectionList.astro, Footer.astro
  scripts/                build checks (meta, JSON-LD, links, shots)
```

Rules:

- One page = one file. File name = URL slug: lowercase, words joined with `-`.
- No trailing slash anywhere. URLs are `/docs/<slug>` (Vercel `cleanUrls`,
  `trailingSlash: false`). Canonical, sitemap and every internal link use that form.
- Do not create `index.md` files in new folders. The hubs are `features.mdx` and `troubleshooting.mdx` next to the folders.

## Frontmatter

Starlight's own fields work (`title`, `description`, `sidebar`, `lastUpdated`,
`head`, `tableOfContents`, `template`, `hero`). On top of them:

| field | type | required | meaning |
| --- | --- | --- | --- |
| `title` | string | yes | H1 and `<title>`. For troubleshooting pages use the exact error text people search. Aim for <= 55 characters: " | Devpit Docs" is appended, and when that passes 70 characters the site uses " | Devpit" instead. |
| `description` | string | yes | Meta description and social text. 70 to 160 characters. Unique on the whole site. |
| `sidebar.label` | string | no | Short sidebar label if the title is long (troubleshooting pages should set it). |
| `sidebar.order` | number | no | Sort order inside an autogenerated folder. |
| `faq` | `[{question, answer}]` | no | Q&A. Emits FAQPage JSON-LD and is also rendered visibly at the end of the page under "Common questions". Answers are plain text, no Markdown, no HTML. Do NOT also write the same Q&A in the body. |
| `related` | string[] | no | Content ids linked in a "Related" box at the end, e.g. `[features/free-up-disk-space, troubleshooting/foo]`. Every id must exist (build fails otherwise). Use 2 to 4. |
| `schemaType` | `TechArticle` \| `Article` \| `none` | no | JSON-LD article type. Default: `TechArticle` under `troubleshooting/`, `none` elsewhere. Blog posts get `BlogPosting` automatically, leave it unset. |
| `published` | date `YYYY-MM-DD` | no | `datePublished` for Article JSON-LD. Only set it if true. |
| `lastUpdated` | date | no | Truthful last edit date. Used for `dateModified` and the sitemap `lastmod`. Omit if unsure. |
| `ogTitle` | string | no | Shorter text for the generated social image (<= 80 chars). |

Every page also gets, with no work: canonical URL, Open Graph and Twitter tags,
a generated 1200x630 social image at `/docs/og/<id>.png`, a BreadcrumbList.

### Troubleshooting page template

```mdx
---
title: "winget error 0x80073D28: app needs administrator rights"
description: "What winget error 0x80073D28 means when updating an app, and how to fix it in three steps."
sidebar:
  label: "winget 0x80073D28"
published: 2026-09-29
related:
  - features/update-everything
  - troubleshooting/app-is-in-use
faq:
  - question: "Is 0x80073D28 dangerous?"
    answer: "No. Windows only says the app must be closed or updated as administrator. Nothing is damaged."
---

Short answer first (one or two sentences).

## Why it happens
## How to fix it
1. ...
2. ...
```

### Blog post template (starlight-blog)

```mdx
---
title: "Free 30 GB by deleting node_modules on Windows"
description: "A safe way to find and delete old node_modules folders on Windows without breaking a project."
date: 2026-09-29            # required, YAML date
authors: [zubair]           # configured author id
tags: [node_modules, disk space]
excerpt: "One sentence shown in the blog list."   # optional
cover:                      # optional, also used as JSON-LD image
  alt: "Devpit showing folders it can delete"
  image: ../../assets/covers/node-modules.png
related: [features/free-up-disk-space]
---
```

Blog URLs: list `/docs/blog`, post `/docs/blog/<slug>`, tags
`/docs/blog/tags/<tag-slug>`, author `/docs/blog/authors/zubair-bin-shaukat`,
feed `/docs/blog/rss.xml`. Reading time is on. starlight-blog emits
`BlogPosting` JSON-LD (author, dates, keywords, image); the site adds
`publisher` and a default image. Blog posts still need a `description`.
Tag, author and page-number pages get their own generated title and
description, are `noindex, follow` and are left out of the sitemap (thin
archive pages); the blog list and the posts are indexed.

## Writing rules

- Very easy English, short sentences, numbered steps. Facts only from the code
  or from a cited source. Never invent error codes, flags or behaviour.
- Links between pages are root-relative WITH the base and no trailing slash:
  `[Free up disk space](/docs/features/free-up-disk-space)`. Link to a heading
  with `#heading-id`. The link validator fails the build on a broken internal
  link or anchor.
- Links to the landing page: `/`, `/install`, `/#faq` are allowed. External
  links use the full https URL.
- Real GitHub repo: https://github.com/zubairbinshaukat/devpit
- Admonitions: `:::note`, `:::tip`, `:::caution`, `:::danger` (with `:::`).
- Show keys with `<kbd>` (needs `.mdx`) or backticks.
- Commands in fenced blocks with a language: `powershell`, `sh`, `text`.

## Images

Screenshots are rendered from the real app, never captured by hand, and
committed to `web/docs-site/src/assets/screens/`, one WebP per manifest entry:
`src/assets/screens/<name>.webp`. `task docs:shots` (repo root) renders them all;
see `src/assets/screens/README.md` for what it needs.

1. Add an entry to `web/docs-site/shots.json` (docs pages) or
   `web/docs-site/shots.content.json` (troubleshooting and blog): a JSON array,
   append and keep it valid. Both files are read and merged; names must be unique
   across them.

   ```json
   { "name": "clean-results", "alt": "Devpit list of junk folders with sizes and risk labels",
     "screen": "clean", "state": "results", "cols": 100, "rows": 30, "note": "optional hint" }
   ```

   `name` is kebab-case and unique. `alt` is real descriptive alt text (15+
   characters). `screen`, `state` and the optional `note` tell the screenshot tool
   what to render; `cols` x `rows` is the terminal size (20 to 300 each).

   Terminal size: at least 80 x 24 (the app draws a "needs a bigger window"
   notice below that). The full list of `screen/state` keys is the scene registry
   in `internal/shots/registry_test.go`; the common ones:

   | screen | states |
   | --- | --- |
   | `home` | `menu` |
   | `firstrun` | `welcome`, `icons`, `theme`, `privacy` |
   | `clean` | `menu`, `picker`, `scanning`, `results`, `confirm`, `summary` |
   | `ports` | `menu`, `kill-port` (the port field), `kill-confirm`, `busy-list`, `node-list`, `summary` |
   | `install` | `list`, `confirm`, `running`, `summary` |
   | `update` | `checking`, `results` (the list of out-of-date apps), `confirm`, `running`, `summary` |
   | `network` | `menu`, `ip`, `ping-input`, `ping-done`, `dns-confirm` |
   | `portsnet` | `menu` (the Ports & Network menu) |
   | `apps` | `menu` (the Install & Update menu) |
   | `settings` | `menu` (the top list), then a row id for a sub-screen: `folders`, `never-touch`, `dev-ports`, `font`, `probe`, `about` |
   | `share` | `sharing` (the host card), `copying` (a copy in progress) |

2. Use it in an `.mdx` page:

   ```mdx
   import Shot from '@/components/Shot.astro';

   <Shot name="clean-results" />
   <Shot name="clean-results" caption="Junk found in a projects folder" />
   <Shot name="home-menu" priority />   {/* only the first image above the fold */}
   ```

   Props: `name` (required), `caption`, `alt` (overrides the manifest), `priority`.
   The alt text comes from the manifest.

3. Rendering uses Astro's image pipeline (sharp): AVIF and WebP at several
   widths with `srcset` and `sizes`, explicit width and height (no layout
   shift), `loading="lazy"` and `decoding="async"`. Only `priority` loads eagerly
   with `fetchpriority="high"`; use it on at most one image per page, the first
   one above the fold.

4. A missing image never breaks `npm run build`: a neutral placeholder that
   reserves the same space is drawn. `npm run check` lists what is missing. Set
   `DOCS_REQUIRE_SHOTS=1` to make a missing image a build and check error.

Other images (blog covers, diagrams): put them in `src/assets/...`, reference
with a relative path in Markdown (`![alt](../../assets/x.png)`) or in the `cover`
frontmatter. Astro optimises them. Always write alt text.

## FAQ JSON-LD

Only through the `faq` frontmatter array (above). The Footer renders the same
questions on the page (Google requires the markup to match visible text) and
`src/routeData.ts` emits the `FAQPage`. `npm run check` validates that every
question has a non-empty answer and that the visible text is present.

## What the build checks (`npm run check`)

- `astro build` itself runs starlight-links-validator: every internal link and
  `#anchor` must resolve, and `related` slugs must exist.
- `check-meta`: every built page has a unique `<title>` (<= 60 chars), a unique
  meta description (70 to 160 chars), a canonical URL that is clean (no `.html`,
  no trailing slash) and matches the file, `og:url`, Open Graph and Twitter tags
  with a 1200x630 `og:image` that exists, one `<h1>`, and is indexable (except the
  thin blog archive pages, which must be `noindex`).
- `check-jsonld`: every `application/ld+json` parses and has what Google asks for
  (`SoftwareApplication`, `FAQPage`, `BreadcrumbList`, `TechArticle`/`Article`,
  `BlogPosting`); FAQ text must be visible on the page; no fake ratings.
- `check-assets`: every internal link, script, stylesheet, image, font and social
  image referenced by a built page exists.
- `check-shots`: manifests are valid, every `<Shot name>` is in one, missing
  images are listed.
- `check-site` (needs `node web/scripts/build.mjs` first): the merged
  `sitemap.xml` lists exactly the indexable pages plus the landing page, robots.txt
  points at it, the landing page is byte-identical to `web/index.html`, and the
  committed `web/llms.txt` is up to date (`node web/scripts/gen-llms.mjs --write`)
  and lists every page by its Markdown twin, with the blog under "Optional".
- `check-markdown` (needs `node web/scripts/build.mjs` first; the build runs the
  same checks and fails on them): every page has its Markdown twin, no twin has
  an `import`/`export` line, a JSX or HTML tag, an MDX comment or a `:::` aside
  left, every link in the twins, `llms.txt` and `llms-full.txt` is absolute and
  points at a page (and `#anchor`) that exists, no twin is in the sitemap, and
  `vercel.json` serves them as `text/markdown` with `X-Robots-Tag: noindex`.

## Markdown twins (for AI agents)

Every page is also served as plain Markdown at its URL plus `.md`
(`/docs/features/accounts.md`; the docs home is `/docs/index.md`).
`web/scripts/md-twins.mjs` makes them at build time from the content sources:
H1 title, the description, the body with MDX turned into Markdown, the `faq` as
"Common questions", `related` as a "Related" list, and the canonical HTML URL as
the last line. Links become absolute HTML URLs.

| In the page | In the twin |
| --- | --- |
| `<Shot name>` | `*Screenshot: <alt from the manifest> (<caption>)*` |
| `<SectionList dir>` | a list of the folder's pages, in the same order |
| `<CardGrid>` with `<Card>` / `<LinkCard>` | one list, one item per card |
| `:::note[Title]` (and tip, caution, danger) | a blockquote starting `**Note: Title**` |
| `<kbd>x</kbd>` | `` `x` `` |
| `import` lines, `{/* comments */}` | removed |

`Aside`, `Steps`, `Tabs`/`TabItem`, `Badge` and `LinkButton` are converted too.
Any other component, an expression attribute such as `title={x}`, or an
`export` fails the build: add its conversion to `md-twins.mjs` first. The
twins are not in the sitemap and are served `noindex`, so search engines only
see the HTML page.

## Not in your way

- The landing page (`web/index.html`) and Vercel functions are untouched by
  the docs build.
- The merged `sitemap.xml`, `llms-full.txt`, the Markdown twins and the sidebar
  entries for the Troubleshooting folder and blog are generated at build time.
  `web/llms.txt` is generated too, but committed: run
  `npm run llms` in `web/docs-site` after adding or retitling a page.
- To add a top-level nav entry, edit `sidebar` in `site.config.mjs`.
